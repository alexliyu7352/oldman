## 2. Tables do not provide sign-in and initialization automatically

The configuration template installs `oldman.auth`, `oldman.apps.admin`, the notifications App, and the demo's business Apps, and enables Session. Auth's concrete User is `apps.accounts.models.User`. Create your own account on the first run with `./run.sh web createsuperuser`.

Account commands (`createsuperuser`, `changepassword`) come from the Auth App.**EPG's management interface is not a site automatically generated by install_admin()**. Account pages such as `/login`, `/users`, and `/user-session` use framework account flows (`LoginFlow`, `AccountFlow`, `UserManagementFlow`, plus `PasswordResetFlow`). apps/accounts/routes.py installs them at addresses configured in `web.account`, just like the dashboard scaffold generated by `startproject`. See the [Admin guide](admin.md) for the built-in Admin site.

WebService first runs framework initialization, then installs StatelessCSRFManager, notification routes, templates and frontend packages (`install_dashboard_templates`), and account pages, followed by token interfaces and the built-in Admin. Jinja's `_` and `gettext` use `oldman.i18n.gettext` directly, rather than a custom wrapper accepting only one string. Table summaries therefore render correctly with parameters and when translation is disabled.

All active accounts can sign in. Example pages, Modals, and write interfaces use the framework's `@login_required()` (`oldman.web.auth`). Reading and writing projects also requires role permissions such as `require_perm(request, ExamplePermissions.view_projects)` or `change_projects` (this is where the demo demonstrates role permissions). Table data enters framework authentication and permission dispatch through `ExampleProjectTable.as_view()`. Do not protect only display pages while exposing data interfaces.

The project list is shared by all signed-in demo users, without filtering by the current user or tenant. When adapting this code for private business data, restrict both list queries and the scope of objects that can be edited or deleted.

## 3. One Table, two rendering formats

`ExampleProjectTable` uses the data route `/examples/tables/projects/table`. The view module registers it explicitly:

```python
router.add_route(ExampleProjectTable.as_view(), ExampleProjectTable.route_path, name=ExampleProjectTable.route_name)
```

In the same module, `_project_table(request)` passes `q`, `team_id`, `status`, `priority`, and `is_active` from the page query as initial state. Do not implement a separate filtering query in the frontend.

The Table's actual configuration includes:

- A default page size of 10 and default ordering of `("-updated_at",)`.
- Search across `name`, `slug`, `description`, and `team.name`.
- Data retrieval with `select(ExampleProject).options(selectinload(ExampleProject.team))`.
- The Team column explicitly declares `field_path="team.name"`, so clicking it sorts by team name, rather than displayed HTML or the relationship object.
- The actions column is not sortable; it outputs buttons that open edit and delete Modals.

The original Team column declaration:

```python
        Column("team", _("Team"), field_path="team.name", callback="get_column_team_data"),
```

`callback` determines the displayed value; `field_path` determines database field mapping. These serve different purposes. Change sorting rules in the Table declaration, rather than guessing SQL fields from frontend text.

The dynamic template connects filters and the table as follows:

```jinja
      {{ filter_form.render(method="get", submit_label=_("Filter"), table_target="#example-projects-table") }}
      <div data-om-component="feedback"></div>
      {{ table.render_shell(
        html_id="example-projects-table",
        show_search=false,
        data_format=table_format,
      ) }}
```

The view passes `table_format` according to `/html` or `/json`. `show_search=false` avoids a second search box because an external filter form already exists. This Table's stable DOM ID is `example-projects-table`; the later reload_table action uses the same target.

## 4. Modal only loads content

The dynamic template imports the shared `modal` macro from `oldman/dashboard/components/modal.html`. The actual container is:

```jinja
  {% call modal(
    "example-project-modal",
    _("Example project"),
    component="modal",
    close_label=_("Close"),
    dialog_scrollable=true,
    inline_hidden_style=true,
    remote_content=true
  ) %}
    <p class="text-default-500 mb-0">{{ _("Choose create, edit or delete to load the real database Form.") }}</p>
  {% endcall %}
```

The “New project” button targets `#example-project-modal` with the remote address `/examples/tables/projects/new-modal`. Inline edit and delete buttons point to the same container, changing only the remote URL.

The complete original view function for the create Modal follows. Its imports and `app` definition are in views/tables.py, listed in this chapter's source table; no separate request client is needed:

```python
@router.get("/examples/tables/projects/new-modal", name="example_project_create_modal")
@add_csrf_token()
@login_required()
async def example_project_create_modal(request: Request):
    """Load a create Form into the shared remote Modal."""
    await require_perm(request, ExamplePermissions.change_projects)
    async with db_manager.get_read_session() as session:
        form = ExampleProjectForm(request=request, session=session)
        html = await form.render(
            action="/examples/tables/projects/create",
            form_mode="json",
            submit_label=_("Create project"),
            validate=True,
        )
    return modal_response(_("Create example project"), html=html)
```

There are three key boundaries:

1. GET generates a CSRF token and renders the Form within an active read-only Session, providing team options from the database.
2. The initial Modal request returns `title/html` JSON, loaded by the shared Dashboard Modal. This is not the actions response for a form submission.
3. The loaded form is still an ordinary Form component. Modal does not parse field errors or implement a second submission flow; new content mounts through the shared component lifecycle.

The edit entry point first reads the real record with `get_object_or_404(session, ExampleProject, project_id, ...)` (`oldman.web.shortcuts`), then builds the same Form using `instance=project`. Missing records should return 404, rather than silently becoming create forms.

## 5. Validate before saving

The complete create handler:

```python
@router.post("/examples/tables/projects/create", name="example_project_create")
@csrf_protect()
@login_required()
async def example_project_create(request: Request):
    """Create one Project and reload the mounted HTML or JSON Table."""
    await require_perm(request, ExamplePermissions.change_projects)
    async with db_manager.get_session() as session:
        form = ExampleProjectForm.from_request(request, session=session)
        if not await form.validate():
            return json_response(form.to_api_response().to_dict())
        await form.save(commit=True, session=session)
    return modal_success_response(_("Project created."), table_target="#example-projects-table")
```

`ExampleProjectForm.Meta.fields` is the allowlist of editable fields; requests cannot use it to update arbitrary model fields. Form retains WTForms fields and synchronous validation, adding actual business cleaning:

- `clean_slug()` checks for duplicate slugs using the current Session, excluding the current instance when editing.
- `clean()` checks that the end date is not before the start date. This is a form-wide error, displayed in the message area at the top of the form.
- Budget must be nonnegative; Progress must be between 0 and 100.
- Team options come from the database; text from the browser does not become an arbitrary valid foreign key.

JSON validation failures return HTTP 200 with a business error code and do not execute save. Form places field errors beside fields and form-wide errors in the dedicated message area. System exceptions, including database constraint violations and connection failures, must not become false successes.

`save(commit=True)` performs add/flush within the current transaction. The success response in the next section is built only after the context exits and commits successfully. A toast received by the browser is not a database commit mechanism.

## 6. Execute UI actions in order after success

The success response is `modal_success_response(_("Project created."), table_target="#example-projects-table")` from `oldman.web.api`. Its expanded payload is:

```python
payload = DefaultApiFormResponse(
    error_code=ApiErrorCode.OK,
    message=message,
    actions=[
        FeedbackAction(title=message, icon="success"),
        CloseModalAction(),
        ReloadTableAction(target="#example-projects-table"),
    ],
)
return json_response(payload.to_dict())
```

The caller supplies translated text for the current request (`str` or `LazyTranslation`), rather than a notification center message.

Actions execute in list order: display success, close the Modal that initiated the request, then refresh the specified Table. Form handles message/errors first, then passes actions to the current Page's Runner. Do not listen for submission success to refresh a second time.

If an action fails, subsequent actions stop. A committed database transaction is not undone by a UI action failure. When the user leaves, the old Page's requests and remaining UI work are abandoned, rather than moved to the new page.

Successful edits and deletions use the same helper and `table_target`, so both HTML/JSON pages share the same UI behavior. The ordinary confirmation Form before deletion is in [delete_project.html](https://github.com/alexliyu7352/oldman-epg-dashboard/blob/main/templates/partials/examples/tables/delete_project.html), including CSRF, message, and status areas. Canceling the Modal sends no delete request; only confirmation deletes the database record through POST.

## 7. Distinguish HTML Tables from HTML Forms

Modals on both Table pages in this chapter submit JSON Forms.**An HTML Table does not require its Forms to use HTML responses**.

To compare the forms' two response modes, open [/examples/forms/basics](http://127.0.0.1:17997/examples/forms/basics) and operate both the HTML response and JSON response actions forms. Their actual code is in [views/forms.py](https://github.com/alexliyu7352/oldman-epg-dashboard/blob/main/apps/examples/views/forms.py), [forms.py](https://github.com/alexliyu7352/oldman-epg-dashboard/blob/main/apps/examples/forms.py), and [forms/page.html](https://github.com/alexliyu7352/oldman-epg-dashboard/blob/main/templates/pages/examples/forms/page.html). The validation page separately demonstrates validation rules and currently mounts only a JSON form; do not look there for a second HTML form.

`_form_error_response()` uses the client's Accept header to return either a JSON business error or error form HTML with HTTP 422. The frontend adapts JSON Form and HTML Form responses into a shared handling flow; this does not mean the backend only supports JSON.

| Scenario | Response consumer |
| --- | --- |
| Full page, sign-in page | Browser/Turbo page navigation |
| Initial Modal title/html JSON | Dashboard Modal |
| Table data HTML or Table-specific JSON | Table |
| JSON Form message/errors/actions | Form and Page Runner |
| HTML Form 2xx/422 fragments | Form's HTML response adapter |
| 401, 403, 5xx, or network failure | Shared authentication, permission, and request error handling, rather than business success |

Ordinary field demonstration pages validate and display data; they do not all write to the database. Actual model-saving examples use this chapter's CRUD, multi-step, JSON List, or upload pages. “Submission successful” does not mean a model has been created.

## 8. How page scripts load and are destroyed

The backend's `_page_context()` passes `page_entry="examples"`. The template inheritance chain is:

`tables/dynamic.html → pages/examples/base.html → base.html → oldman/dashboard/base.html`。

The project's base.html uses the shared `dashboard_main_frame()`. The page entry is written to both body and the main Frame. frontend/src/main.ts's `pageLoader` uses this name to import `pages/examples.ts`, which calls `setupPage("examples", ExamplesPage)`.

ExamplesPage extends the project's BasePage, which extends the framework's DashboardPage and already integrates shared Form, Modal, Table, and Feedback loaders. Private loaders such as realtime tables are declared only in ExamplesPage, rather than globally. The example has no additional FormModal.

When switching pages through the sidebar, the unified lifecycle unmounts the old Page, replaces the main Frame, and creates the target Page. Although both example URLs use ExamplesPage, they still create separate instances. Loading a Modal or replacing a form fragment within the current page updates only affected components, without destroying the entire Page.

See the [Frontend reference](../developers/frontend.md) for cancellation, cleanup, main Frame, and Feedback rules. Registering all components globally does not fix an unloaded entry point for an individual page.

## 9. Verify through real operations

These operations modify demo data. Run them only in your own test database, using temporary projects you created. Do not delete teams or preset business records.

1. Open HTML/JSON tables directly while signed out; you should reach the sign-in page. An incorrect password should show a clear sign-in error; the correct password should open the page.
2. On each page, search project names, filter by Team/Status, change pages, and click Team to sort in both directions. Network data formats differ, but the data source is the same.
3. Open the create Modal and enter a unique slug. First set the end date before the start date: submission should display an error at the top without creating a record. Correct the dates and save: the Modal should close, success should appear, and the list should refresh.
4. Edit the project just created, using another existing project's slug. Submission should display a field error and preserve the original record. Save a valid value, then reopen to check the data.
5. Click delete and cancel first; the record should remain. Confirm deletion next; neither table should show the row after querying again.
6. Enter through the sidebar from a non-example page, then switch between HTML/JSON examples and repeatedly open and submit Modals. A successful direct refresh does not replace Turbo navigation verification.
7. Inspect Form requests in the browser: JSON validation failure should be an HTTP 200 business error, rather than 422. Test HTML 422 separately with the HTML form on basics. Native browser validation may intercept input first. Use developer tools to inspect actual requests when checking backend responses; an unsent request is not a backend response.
8. Simulate request failure on your own isolated service. Confirm that page navigation removes the loading overlay and shows an error, while the old page remains usable. Do not stop someone else's demo for verification.
9. Query again after refreshing and restarting your own service. Determine persistence from the database and fresh queries, rather than toasts.

Client-side required validation may block submission before a request is sent. Use duplicate slugs or reversed dates to test backend business validation without disabling browser security settings. Pagination requires more than 10 matching records; filtering down to one result cannot verify multiple pages.

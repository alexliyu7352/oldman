# Pages, components, and dynamic content

`oldman-web` is a native TypeScript browser package requiring neither React nor Vue. Backend HTML declares pages/components, the entry point starts the runtime, and the component manager mounts/cleans up components. See [Frontend assets, styles, icons, and translation](assets.md) for installation/building and [Demo HTML/JSON tables and Modal forms](../users/tutorial-dashboard.md) for actual CRUD wiring.

Agents: before writing code, read the [dashboard CRUD guide](../agents/dashboard-crud.md). It says which interface the task needs, how to wire it and what counts as done.

## Demo dashboard page entry point

The actual entry point is [EPG frontend/src/main.ts](https://github.com/alexliyu7352/oldman-epg-dashboard/blob/main/frontend/src/main.ts), rather than a separate startOldman call per page. Like the dashboard scaffold generated by `startproject`, it calls framework `startDashboard()` (see [the framework startup entry point](#framework-startup-entry-point)) and supplies only styles, the language contract, a fallback page, and on-demand page modules. Complete file:

```typescript
import "@app/css/app.css";
import { BasePage } from "@app/pages/base-page";
import { startDashboard } from "oldman-web/dashboard";
import { defaultLanguage, languageAliases, languageDefinitions, languagePreferencePath } from "./i18n/generated";

// The sign-in and password reset pages are the framework's: startDashboard mounts its AuthPage on them.
const pageEntries = import.meta.glob([
  "./pages/backend.ts",
  "./pages/examples.ts",
  "!./pages/**/*.test.ts"
]);

void startDashboard({
  i18n: {
    aliases: languageAliases,
    defaultLanguage,
    languagePreferencePath,
    languages: languageDefinitions
  },
  // Unknown entry names (a typo, a page without its own pages/<name>.ts) still get the dashboard base page.
  fallbackPage: BasePage,
  pageLoader: async (pageName) => {
    const loader = pageEntries[`./pages/${pageName}.ts`];
    if (loader) await loader();
  }
}).catch((error: unknown) => {
  console.error("Dashboard startup failed", error);
});
```

Sign-in/password-reset pages are absent from this page list because they belong to the framework. `startDashboard` registers framework `AuthPage` as `login`.

Ordinary business pages in [backend.ts](https://github.com/alexliyu7352/oldman-epg-dashboard/blob/main/frontend/src/pages/backend.ts) inherit project BasePage and call `setupPage("backend", BackendPage)`. Example pages register `setupPage("examples", ExamplesPage)` in [examples.ts](https://github.com/alexliyu7352/oldman-epg-dashboard/blob/main/frontend/src/pages/examples.ts), supplying their own loaders/actions.

The server selects the example entry with `page_entry="examples"`. Shared templates mark both body and the main Frame emitted by `dashboard_main_frame()` with the same page name; marking only body, which does not change during Frame navigation, is insufficient. setupPage registers constructors, then PageRegistry creates instances. If a name is unregistered and `pageLoader` finds no module, the registry uses the class from `startOldman({ fallbackPage })` (`startDashboard` forwards it unchanged; the demo supplies project BasePage, Admin supplies AdminPage), logging `No page registered for …`. Without a fallback, it still throws. Fallback allows shell components to mount despite a misspelled name, but page-specific loaders/actions still require correct registration.

BasePage in the project's [base-page.ts](https://github.com/alexliyu7352/oldman-epg-dashboard/blob/main/frontend/src/pages/base-page.ts) **belongs to the application** and inherits framework DashboardPage. Do not confuse it with framework BasePage exported by `oldman-web/app`. It merges shared Dashboard loaders with application overrides. Plain-HTML business pages still need this runtime to mount components, without separate private Page logic.

See [Frontend assets, styles, icons, and translation](assets.md) for complete asset/translation wiring. Both direct visits and sidebar navigation in the demo should pass through this entry point. Do not move private loaders globally to compensate for failed Page switching.

Elements marked `data-om-i18n-key="<msgid>"` in templates have their
**entire textContent overwritten** by `i18n.translateDocument()` at startup and on each language switch.
Because it replaces content, mark text-only elements rather than nodes also holding business data. Most cases do not need it:
server-rendered text is translated directly by Jinja gettext.

## Framework startup entry point

`oldman-web/dashboard` exports `startDashboard(options)` to perform dashboard/built-in Admin startup together: create HTTP Client (401 redirects to the server-supplied `login_url`), i18n, and OldmanContext; await language initialization; register the authentication page at `AUTH_PAGE_NAME` (`"login"`, its `data-om-page` value); then call `startOldman`. Repeated calls return the same application, and failed startup can be retried. `stopDashboard()` supports tests and whole-page teardown.

`options.i18n` defines the language contract: `languages`, `defaultLanguage`, optional `aliases`, `languagePreferencePath`, and optional `initialCatalog`. Projects generate languagePreferencePath with `i18n compile-frontend` from `i18n.preference_url`, the sole writer of the language Cookie. null means the page has no such endpoint and is intended only for single-language pages. On multilingual pages outside path mode, null causes navigation after switching to revert to the old language; see [which language a request uses](assets.md#which-language-a-request-uses). Other options are `assetBaseFallback`, `fallbackPage`, `pageLoader`, and `authPage`. `authPage` defaults to framework `AuthPage`, mounting only forms, language switching, and preloading without a dashboard shell. Built-in Admin, the dashboard scaffold, and the EPG demo all start through it.

## Responsibilities of the three object layers

| Object | Origin and responsibility |
| --- | --- |
| `OldmanContext` | `createOldmanContext()` / `getOldmanContext()`; shared i18n, HTTP, logging, asset URLs, and registries |
| `Page` / `BasePage` / `DashboardPage` | PageRegistry creates/owns the current instance; manages page resources, components, and response Runner |
| `Component` | Page's ComponentManager creates it from DOM; manages one DOM region's interaction and cleanup |

`Page` in `oldman-web/core` provides `root`, `signal`, `http`, `i18n`, `logger`, `components`, `responseActions`, and optional `feedback`. `BasePage` in `oldman-web/app` adds declarative loaders, dynamic component content, initial loading, and main-Frame request-state handling. `DashboardPage` in `oldman-web/dashboard` additionally installs Sidebar, Topbar, default Feedback, back-to-top, and shared theme behavior. The unified Page lifecycle installed by `startOldman()` coordinates business-page teardown, entry loading, and new Page mounting. An old BasePage does not take over a new page's private components.

The dashboard itself is a Page. Its shell Feedback becomes the Page default, reused by ordinary child pages without another global feedback path. Custom business Pages should inherit DashboardPage; low-level Page does not automatically have a shell, loaders, or Feedback.

## Lifecycle and cleanup

Page hooks are `beforeMount()`, `mount()`, `afterMount()`, `beforeUnmount()`, and `unmount()`. Overrides of existing BasePage/DashboardPage hooks must call super or component/shell initialization is skipped.

`this.on()` / `this.onCustom()` delegate events; `this.listen()` targets specific objects; `this.timers` manages timers; `this.cleanup(callback)` registers custom resource cleanup. Page destruction aborts signal and runs registered cleanup. DOM removal alone does not remove external subscriptions, native timers, or third-party instances.

The private-action example uses the demo's actual `example_mark`, not another unwired action. Below is the original ExamplesPage method; the file already imports ResponseAction/ResponseActionContext:

```typescript
  override async handleResponseAction(
    action: ResponseAction,
    context: ResponseActionContext
  ): Promise<boolean> {
    if (action.action !== "example_mark") return super.handleResponseAction(action, context);
    if (typeof action.target !== "string" || typeof action.text !== "string") {
      throw new Error("Example mark Action requires a target and text");
    }
    const target = this.root.querySelector<HTMLElement>(action.target);
    if (!target) throw new Error(`Example mark Action target was not found: ${action.target}`);
    target.textContent = action.text;
    return true;
  }
```

The backend's example_action_private in [views/modals.py](https://github.com/alexliyu7352/oldman-epg-dashboard/blob/main/apps/examples/views/modals.py) returns _ExampleMarkAction, available at `/examples/modals/actions`. Unknown framework actions first go to the current Page, where true means handled; there is no extra global event protocol. See [ordered actions](responses.md) for exact rules.

## Component registration

Dashboard defaults to `#oldman-main` for the business-page Frame. To customize it, set `mainFrameSelector` once in top-level Page constructor options, for example `super({ root, mainFrameSelector: "#workspace-main", componentLoaders: createDashboardComponentLoaders() })`, and use the same target in HTML Frames, navigation links, and responses. Page lifecycle, in-Page sidebar, and notification center read `page.mainFrameSelector`; `sidebarOptions` does not define a second main Frame. Standalone `DashboardSidebar` without a Page can still use its own options. Handwritten main Frames also require `data-om-page`; nested Frames for partial updates do not rebuild the Page.

Dashboard light/dark theme is persistent: topbar changes write `dashboard.theme` in `PreferenceStore` (localStorage key `oldman:dashboard.theme`), retained across reloads/new tabs. Without a record, it follows system `prefers-color-scheme`, then template defaults. `oldman/dashboard/base.html` runs the inline `partials/theme_boot.html` script in `<head>` before styles to set `data-theme` and prevent a light-to-dark flash. Desktop sidebar width persists only during page switching within one browser document; defaults apply at document initialization, and reload does not preserve it. SidebarMenu closes mobile sidebar overlays during component cleanup; business Pages need no duplicate cleanup.

PageRegistry coordinates Page teardown: ComponentManager handles ordinary components, and Page cleanup callbacks run last. Dashboard shell SSE, notifications, and components register on the existing cleanup stack. Failed cleanup logs an error and allows other cleanup to continue. Register extension resources through `this.cleanup(...)`; calling `beforeUnmount()` alone is not complete destruction, and ordinary components must not be unmounted twice.

The demo's `templates/pages/examples/tables/dynamic.html` emits the Table shell with `table.render_shell(html_id="example-projects-table", data_format=table_format, ...)`; see [the tutorial](../users/tutorial-dashboard.md#3-one-table-two-rendering-formats) for the complete call. Do not invent a minimal business-template container inconsistent with server Table output.

Every component name needs a loader. `createDashboardComponentLoaders()` supplies all framework loaders and replaces modal/feedback with shared Dashboard theme adapters. `createDashboardCrudComponentLoaders()` is a lightweight boundary including only sidebar-menu and table. Explicitly add Form/Modal when needed; it is not equivalent to the complete loader set.

Import ordinary components on demand from `oldman-web/components/<name>`, and Dashboard Modal/Feedback from `oldman-web/dashboard/modal` and `oldman-web/dashboard/feedback`. The library owns third-party dependencies. Do not copy Choices, TanStack, or Modal submission flows into business code.

Dynamic HTML first unmounts old components, inserts new content, loads required constructors, and mounts them. Built-in Form, Table, Modal, and replace_html use the same component manager. Main-Frame business navigation cleans up through Page teardown/mounting. Custom complex fragments must use that manager too; source assertions or innerHTML replacement alone do not establish correct lifecycle handling.

Declare page-private component loaders only on their Page rather than globally. In the complete EPG demo's `frontend/src/pages/examples.ts`, `ExamplesPage` supplies `realtime-table`, `example-chart`, `navigation-probe`, `icon-catalog`, `feedback-workflow`, and other loaders in its constructor, and handles `example_mark` in that same class. Components live in `frontend/src/components/examples/`. The `pageLoader` in `frontend/src/main.ts` loads `./pages/examples.ts` by entry name, and backend example views pass `page_entry="examples"`. Both dashboard-sidebar navigation and direct visits create this Page. Do not move loaders to shared BasePage to compensate for a page entry that did not switch.

## Feedback interactions and real requests

Confirmation dialogs must wait for user choice; display-only `FeedbackAction` cannot replace them. The actual consumer is EPG [FeedbackWorkflow](https://github.com/alexliyu7352/oldman-epg-dashboard/blob/main/frontend/src/components/examples/feedback-workflow.ts) at `/examples/messages/feedback`. It imports Component from `oldman-web/core` and Feedback from `oldman-web/components/feedback`. During mount, it obtains `this.root` and `this.page?.feedback`, checking HTMLFormElement and Feedback respectively. Dashboard prepares themed Feedback before ordinary content mounts. The type check enables confirm/prompt access; it does not create an instance.

A native form holds project_id, the request URL, and the returned-HTML target. Its `data-om-action="post"` lets manual `runAction` read parameters. It has no ordinary `form` loader, and both buttons use `type="button"`. The component prevents native submit and binds clicks itself. Do not add ordinary Form automatic submission on top.

The component's original confirmation branch follows. feedback is the instance checked in mount; projectName comes from the selected option:

```typescript
          const confirmed = await feedback.confirm({
            title: this.i18n.t("Move this project to review?"),
            text: projectName,
            icon: "question",
            showCancelButton: true,
            confirmButtonText: this.i18n.t("Move to review"),
            cancelButtonText: this.i18n.t("Cancel")
          });
          if (!confirmed) return;
```

The input branch calls `feedback.prompt<string>`, setting the old name with `inputValue`, labeling its purpose with `inputLabel`, and validating trimmed length through `inputValidator`. It checks `result.isConfirmed` before reading `result.value`. Checking only value would confuse cancellation with a valid empty result. This business example rejects empty names; the server independently enforces the same rule.

After awaiting the user result, check `this.signal.aborted` before sending. The original request code follows: operation comes from the button, name from confirmed input, and form is the native parameter form:

```typescript
        if (this.signal.aborted) return;
        const response = await this.preloader.withLoading(() => this.runAction(form, {
          params: { operation: operation ?? "", name },
          signal: this.signal
        }));
```

`runAction` reuses shared HTTP, CSRF, and Page Runner without handwritten fetch, copied parsing, or new built-in actions. `withLoading` displays a local overlay only during the confirmed request. The component disables both buttons from dialog opening through completion and restores them in finally. Shared handling displays ordinary network/HTTP/business errors; the component catch only handles dialog/other invocation exceptions and stops silently on cancellation rather than showing another "Request failed". Component lifecycle releases listeners.

Backend [example_feedback_project](https://github.com/alexliyu7352/oldman-epg-dashboard/blob/main/apps/examples/views/messages.py) uses csrf_protect and framework login_required, checking operation, project_id, name, and record existence. Repeated submissions in review status return a nonzero business code rather than success. On success, it exits db_manager.get_session's transaction before rendering `_project_result.html`, returning `data={id,name,status}`, ReplaceHtmlAction, and FeedbackAction. The template escapes names normally; renaming does not change slug. On successful data, the browser updates the option text so another input does not show the old name.

Verification should cover cancellation without POST, real database updates, business rejection, recovery after 403/offline errors, narrow screens/keyboard, and Turbo departure. If a returned response is held in the browser and released after navigation, the old component's request is cancelled, and its result/toast must not affect the new Page. The server may already have committed, so returning reads the new value. This example promises no database cancellation and adds neither navigation locks nor durable compensation.

## Modal is only a container

The demo's [tables/dynamic.html](https://github.com/alexliyu7352/oldman-epg-dashboard/blob/main/templates/pages/examples/tables/dynamic.html) creates `#example-project-modal` with the shared `modal` macro. Buttons point `data-om-modal-target` to it and `data-om-modal-url` to create/edit/delete views. See [the tutorial](../users/tutorial-dashboard.md#4-modal-only-loads-content) for the complete macro, GET, and submission source; no separate HTML shell is needed.

To generate an embedded Modal in Python (such as a table-cell evidence panel), use `await render_modal(request, modal_id=..., title=..., body=...)` from `oldman.web.components`. In table cells, make the column callback `async def`; `request` is available in callback kwargs. Parameters match the macro (`component`, `close_label`, `footer_close_label`, `dialog_class`, `managed`, `hidden`). Do not handcraft the `modal_*` variables from `modal_fragment.html`; one misspelling can produce an empty shell.

Declarative remote loading uses Modal parts JSON, generally title/body/footer. The demo's Dashboard Modal actually accepts `{"title": "...", "html": "<form>..." }`, loading html into the content area. This is not ResponseAction JSON. Generate the payload with `oldman.web.api.modal_response(title, html=...)` or `modal_response(title, body=..., footer=...)` rather than a handwritten dict. Read-only modals get their single close button through `close_label=_("Close")`. For missing objects use `modal_not_found_response(title, message)` (404 with one muted line: a stale browser list is normal, not 500). `loadParts(url)` handles parts; use `loadContent(url)` for actual HTML HTTP responses. Do not confuse the methods.

Declarative triggers load successfully before opening. Failure sets error status and dispatches om:modal:error without opening unloaded content. The shared click entry point also notifies through the owning Page's existing Feedback, following [the response reference](responses.md): framework response `message`, otherwise "Permission denied" or "Request failed". The demo needs no extra listener showing the same error again. Cancellation from navigation/destruction stays silent rather than carrying old-page failures onto a new page.

Direct `loadParts/loadContent` calls still throw original exceptions to business callers without automatically showing Feedback; callers follow their own interaction flow. Standalone low-level Modals without Pages log the original declarative-click error rather than creating global Feedback. Status text inside hidden containers is not visible error feedback. Pages needing user notifications should supply Page/Feedback and show each failure once at the entry point owning that request.

Public methods include `open(trigger?)`, `close(reason?)`, `setContent(content)`, `setParts(parts)`, `loadParts(url)`, `loadContent(url)`, `setStatus(status, message?)`, and `destroy()`. Remote loads unmount old children and mount new ones. Simple setters only change content and are not equivalent to the full remote lifecycle.

Forms in dynamic Modal content still declare `data-om-component="form"`. Submission responses can update Forms, close Modals, reload Tables, or redirect through Form/Runner. There is no Modal-specific field-validation/save protocol.

`om:component:before-dynamic-content-mount` allows synchronous callbacks to register asynchronous loaders with `detail.waitUntil(promise)`. BasePage handles normal loaders already. Only custom loading mechanisms need listeners, not every business Modal.

The `modal` macro's `description` adds one 14px explanatory line beneath the title. Padding is 24px, with 16px between header/body/footer and no dividers. Footer buttons align right and stack on narrow screens. Confirmation dialogs use `dialog_class="om-modal-dialog-sm"` (416px) and the `confirm_body(title, description, icon=, tone=, title_tag=, wrapper_class=)` macro from `oldman/dashboard/partials/confirm.html`. It emits `om-confirm-icon om-confirm-icon-danger|warning|success|info`, `om-confirm-title`, and `om-confirm-description`; do not rewrite these class lists. Pointer-hover Tooltips wait 200ms by default (`data-om-delay="0"` disables delay); keyboard focus shows immediately. Floating positions round to whole pixels. Page navigation uses a top 2px brand-color progress bar, driven by preloader through Turbo visit/frame/submit events. A full-screen overlay appears only on initial load.

DashboardModal adapts theme selectors, focus, animation, and backdrop. `data-om-keyboard="false"` disables Escape closure; `data-om-backdrop="static"` disables outside-click closure. Preserve dialog semantics, title association, accessible close buttons, and keyboard operation rather than copying another Modal for appearance.

## Table operations

Import `Table` from `oldman-web/components/table`. Obtain mounted instances through `page.components.get(element)` and check the instance type before calling:

- `await table.reload()`: request again using the current source URL, pagination, search, and filters.
- `await table.refresh(url)`: explicitly request a URL.
- `await table.applyFilterForm(form)`: connect a filter form to the same Table.

Server-side Forms can simply use `ReloadTableAction` without refreshing again in om:form:success. Table handles loading, obsolete requests, and dynamic mounting. It has no public updateCell API. Pages can locate stable row/column DOM for live display, but that does not modify the database or plugin data.

## HTTP, Actions, and navigation

`page.http` is the shared Client bound to the Page signal. `getJson<T>()`, `postJson<T>()`, and `html()` return data; `postForm<T>()` returns status/data. Default HTTP timeout is 30 seconds. Requests add X-Requested-With, and writes read an available CSRF token. Custom fetch calls do not automatically gain these behaviors.

General `data-om-action` supports small declarative HTML requests, with remote success always returning actions JSON. URLs come from explicit data-om-url, href, form action, or similar sources. Targets follow the response protocol. Do not install both Form submission and data-om-action submission listeners on one Form.

`data-om-confirm` confirms before requesting. startOldman defaults to native browser confirm; cancellation sends nothing. The actions.confirm option can supply themed confirmation, but the EPG deletion example uses [an ordinary confirmation Modal Form](../users/tutorial-dashboard.md#6-execute-ui-actions-in-order-after-success), not another configured confirmation callback. Do not call startOldman a second time to copy this example.

Both Turbo full-page visits and `#oldman-main` business navigation clean up the old Page and create a new one. Once the main Frame receives its response, the unified lifecycle pauses/resumes Turbo rendering to await asynchronous old-Page cleanup before replacing DOM and loading/mounting the target Page. Sidebar/topbar DOM can remain, but their old Page, events, timers, and SSE are released normally, and the new Page owns fresh resources. There are not two instances for a persistent shell Page plus business sub-Page.

Even two URLs using `ExamplesPage` create different instances on navigation. Imported JS modules/Page classes are cached, not departed instances. A handwritten main-Frame response should include `<turbo-frame id="oldman-main" data-turbo-action="advance" data-om-page="examples">…</turbo-frame>` with matching body/Frame entry names. Missing new entry names reuse the current entry but still rebuild the instance. Prefer shared macros over repeating attributes. Similarly, `sidebar_menu_link(href, label, icon=, active=)` in `oldman/dashboard/partials/shell.html` emits flat items with narrow-sidebar tooltips. `{% call sidebar_menu_group(panel_id, label, icon, active=) %}` plus `sidebar_menu_item(href, label, active=, turbo=)` emits expandable groups. Use `turbo=false` for links leaving this shell, such as built-in `/admin`, which has its own layout/assets and needs a full-page visit rather than main-Frame replacement. Macros own `data-om-menu-*` and active/hidden states. Authentication pages use `{% call auth_layout(brand_href, brand_name) %}` from `oldman/auth/partials/auth_layout.html` for top-right language switching, branding, the card, and `oldman-footer-auth`. Later document-level Frame-navigation events do not remount or clear new-component loading again. Browser back/forward uses the corresponding restoration lifecycle.

Form, Table, Modal, and `ReplaceHtmlAction` partial updates within the current page are not business navigation: only affected components unmount/mount. In particular, an Action replacing its own source Form does not stop subsequent actions in the same list or count as user departure. Actual navigation, reload, or closure abandons old responses and remaining UI Actions without waiting or resuming on the new Page. Browser cancellation does not guarantee server rollback of processed requests.

The old Page is not destroyed before the new-page response arrives. Navigation failure retains the original page, stops loading, and shows existing Feedback. Link prefetch is disabled. Do not add Prefetch for partial refresh or a site-wide navigation lock that waits for tasks.

Page/Component immediately abort their `signal` on entering `unmounting`, before cleanup callbacks finish. Page cancellation also cancels its components. The framework then sequentially cleans up ordinary components, shell, and other registered resources before Turbo replaces DOM. Mounting can be cancelled while waiting for page/component modules. Old downloads may continue, but late results must not remount old pages, unmount new pages, or tear down the active global runtime.

The framework checks cancellation between mounting steps it controls. JavaScript cannot forcibly interrupt custom asynchronous hooks. Use `this.http` for request cancellation. After awaiting other operations, call `this.signal.throwIfAborted()` before modifying DOM, registering resources, or starting subscriptions. Unmount hooks release existing resources; do not start business requests through already-aborted Page/Component HTTP Clients. Navigation cancellation ends old mounting normally. Actual errors in an active mount still report and clean up acquired resources.

Stop loading and show existing Page Feedback on request failure. Cancelling old requests is not a user-confirmation error. Verify dynamic updates, browser back, departure during loading, and server outages in a real browser, rather than merely observing endpoint 200 responses.

For HTML errors on main-Frame navigation, Turbo still displays the error page. For plain-text/JSON HTTP errors, BasePage stops the overlay and uses existing Page failure feedback while retaining the old page. This fallback neither executes error-response actions nor handles Forms, other Frames, or normal responses.
